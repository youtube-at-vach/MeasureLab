数値定義・容量・互換性・許容差の正本は実装とテストに置く。実装済み機能の操作・内部構造は各文書へ分け、この計画には残る課題と完了条件を置く。

### 多言語対応（i18n）：I1〜I5完了、I6は翻訳の視覚レビュー

YAMLと`rust-i18n`を使い、英語（`en-US`）を基準に既存9言語へ対応する。基盤・英語キー化の着手は、UI操作調整の完了を前提にしない。文言変更による再翻訳は、基盤・英語キー化と他言語翻訳を分け、翻訳対象を差分に限定して抑える。

I1の検査・翻訳元ハッシュ・差分JSON・CSV・CI、I2の`desktop`限定共通API・英語フォールバック・表示キャッシュ・言語設定・フォントと、I3の現行GUIの英語キー化を実装した。共通メニュー・入出力・状態表示と7計器の見出し・操作・案内・ツールチップ・無効理由・軸の説明を共通APIへ集約し、列挙型の表示名はGUI側で対応付ける。保存・Autosetの通知は引数を保持して表示時に解決し、ウィンドウ・折りたたみは固定IDを使う。`View → Language`の選択はeframeの利用者設定へ保存し、未知localeと欠落・未確認・古い訳は英語へ戻す。I4では英語を基準に、日本語・フランス語・ドイツ語・スペイン語・ポルトガル語・ロシア語・中国語・韓国語の全グループを初回翻訳した。翻訳本文の網羅と実際のGUIでの読み取りやすさは別に判定し、視覚レビューをI6として進める。手順は [開発・翻訳手順](I18N.md)、検査は [検査の回帰テスト](../../scripts/test_i18n.py)、実行時の合否は [共通APIのテスト](../../src/i18n.rs) と実ウィジェットQAを正本とする。

#### 開発と翻訳の分離

* **通常の機能開発は、必要な英語キー・英語文言・呼出箇所だけを追加・変更する。他言語の翻訳・一括同期・英語文言のコピーによる穴埋めを行わない。AIにも全言語の翻訳を指示しない。** 英語キーの削除後に残る旧訳の整理も、翻訳タスクへ差分として渡す。
* 翻訳は明示的に分けたタスク／PRで行う。対象言語・機能グループ・基準リビジョンを指定し、追加・変更されたキーだけをAIへ渡す。既存訳は用語の参考にできるが、無関係なキーを書き換えない。
* このルールは`AGENTS.md`と [開発・翻訳手順](I18N.md) に反映済み。通常の開発コマンドとCIは検査・差分出力だけを行い、翻訳生成や翻訳ファイルの自動修正を呼び出さない。PRの変更範囲を検査し、機能実装と他言語本文の変更を混在させない。
* 基盤・英語キー化の完了と、各言語の翻訳完了を別に判定する。英語を変更した機能PRは、他言語の未翻訳を理由に停止させない。

#### 翻訳資産とGUI境界

* 正本は`locales/<group>/<locale>.yml`とし、例として`locales/common/en-US.yml`、`locales/oscilloscope/ja.yml`を置く。YAMLは言語別形式（`_version: 1`）を使い、本文にも`common.*`、`oscilloscope.*`の名前空間を明示する。ディレクトリ名だけでキーに接頭辞が付くとは仮定しない。`common`、共通画面・入出力、`oscilloscope`、`spectrum`、`spectrogram`、`xy`、`generator`、`lockin`、`comparison`を目安に分け、ウィジェット単位には細分化しない。
* `rust-i18n`の[言語別YAML・フォールバックの仕様](https://docs.rs/rust-i18n/4.2.2/rust_i18n/)と[再帰読込・同一言語の統合処理](https://github.com/longbridge/rust-i18n/blob/v4.2.2/crates/support/src/lib.rs)を基に、分割ファイルをコンパイル時に埋め込む。採用版は導入時にRust 1.95・既存依存との互換性を確認する。翻訳ファイルの実行時読込は初期範囲に含めない。
* 既存9言語は`v0.9.1`の管理済み資産で確認できる英語・日本語・フランス語・ドイツ語・スペイン語・ポルトガル語・ロシア語・中国語・韓国語とする。旧`en`は`en-US`へ対応付け、他は既存の`ja`／`fr`／`de`／`es`／`pt`／`ru`／`zh`／`ko`を初期識別子とする。旧キー・旧GUI・未実装機能の訳を一括移植せず、現在のRust GUIの英語を正本にする。
* GUIは`src/i18n.rs`に設ける共通インターフェースだけを使い、`rust-i18n`の初期化・検索・変数展開・locale操作をその内部へ局所化する。依存とモジュールは`desktop`機能に限定し、GUIなしの測定コアへ持ち込まない。意味を表す安定キーと名前付き変数（`%{name}`）を使い、文章の断片連結や表示文言からのキー生成を避ける。列挙型の表示名もGUI側でキーへ対応付ける。
* 初期言語は`en-US`とし、GUIから実行中に変更できるようにする。選択はeframeの利用者設定へ保存し、再起動時に復元する。未知・廃止localeや未翻訳キーは`en-US`へ戻す。言語を測定条件・結果の識別や入出力開始の契機にしない。
* コールバック、測定・解析・Generatorワーカーには翻訳API・locale状態を渡さない。GUIに表示する状態・エラーは識別子と引数を表示境界で翻訳し、低層の外部エラー詳細は原文を保持する。測定値・単位の定義、JSONのフィールド・enum値、CSVの機械可読形式、ログ識別子は言語に依存させない。数値書式の地域別変更は別の計画とする。
* 引数のない固定文言は借用またはlocaleごとの有界キャッシュで再利用し、毎フレームの`String`化・重複検索を避ける。動的文言はlocale・引数・状態が変わったときだけ更新し、無制限の値別キャッシュを作らない。言語変更で表示キャッシュを無効化し、再描画する。
* eguiのウィンドウ・折りたたみ・編集・選択のIDは翻訳文言から分離し、切り替えで配置・フォーカス・操作対象を失わないようにする。CJK・キリル文字・アクセント付き文字を含むフォントと同梱ライセンスを確認し、通常幅・狭幅・表示倍率変更で単位・主要値・停止操作を確保する。

#### 差分抽出・検査・レビュー用出力

`scripts/i18n.py`へ`check`／`diff`／`export-csv`をまとめ、同じキー正規化と変数解析を使う。Python 3.12以降と`.venv`を使い、旧アプリの翻訳ツール・依存環境は復元しない。

* `diff`は指定したGit基準との英語カタログ比較から、追加・文言変更・変数変更・削除を検出する。キーを維持した文言変更も対象とし、ファイル移動だけなら再翻訳にしない。初回翻訳は対象言語に欠けるキーを差分として出す。
* 翻訳が複数の機能PRより後になる場合に備え、言語・キーごとの翻訳元英語のハッシュを、`rust-i18n`の読込範囲外のメタデータで管理する。メタデータは翻訳PRだけで更新し、英語変更後の要再翻訳を次のPRでも検出する。旧訳は要確認として扱い、現行英語との整合が確認できないキーは共通APIで英語へフォールバックする。
* AIへ渡す差分にはキー、グループ、旧／新英語、必要な変数、対象言語の現行訳、翻訳元ハッシュを含める。削除は整理対象として分ける。適用時は対象キー・変数・翻訳元ハッシュを再検査し、抽出後に英語が変わった訳や対象外キーの変更を拒否する。
* `export-csv`はキー・グループ・英語・各言語・未翻訳／要確認状態を安定した順序で出力し、改行・引用符もエスケープする。CSVは必要時のレビュー成果物とし、YAMLを正本に保つ。初期範囲にCSVからの逆インポートは含めない。

検査は次の区別でCIへ組み込む。未翻訳の検出は欠落・空値・翻訳元の変更を基準にし、英語と同じ表記の専門語・記号だけで未翻訳と判定しない。

| 検査対象 | CIの扱い |
| --- | --- |
| YAML構文・型、同一ファイル内の重複、同一localeの全ファイルを横断した最終キー重複・名前空間衝突 | 全言語でエラー。統合処理による上書きで重複を隠さない。対応するキーが別localeにもあることは正常 |
| 呼出キーの英語定義欠落、空の英語、英語の変数と呼出引数の不整合 | エラー。動的なキー組立を避け、必要な列挙は検査可能な一覧にする |
| 新規・更新した翻訳の変数名の欠落・余分な変数、差分外の書換え、翻訳元ハッシュの不整合 | エラー |
| 他言語の欠落・空値・英語変更で古くなった既存訳、英語から削除済みの旧キー | 原則警告。古い訳に変数差分がある場合も、未翻訳として英語へ戻して機能PRを妨げず、翻訳PRで修正する |

`locales/`、翻訳メタデータ、検査スクリプト、共通APIの変更を`scripts/ci_changes.py`で分類し、YAMLだけのPRでも検査を省略しない。`.github/workflows/ci.yml`の必須チェックへ構造検査と警告一覧を組み込み、未翻訳をCI成功のために自動補完しない。重複・構文不正・変数差分・英語変更・削除・移動・差分適用の競合を検査コードのテストで固定する。

### コード品質の継続QA

新機能の追加とは分け、保存結果の検証・数値の有限性・欠落と世代・ワーカーのロック寿命を優先して点検する。不具合は修正前に失敗する回帰テストで確認し、共通演算の整理は同じ入力条件・精度の利用箇所に限る。

* 安全性と失敗の見落としに関するlintを`Cargo.toml`で個別に有効にし、既存の全ターゲット・全機能Clippyの`-D warnings`で継続検査する。ライブラリでは`unsafe_code`をdenyにし、macOS活動トークンを所有する`activity`モジュールだけを明示的な例外にする。unsafe操作は明示的なブロックに閉じ、各ブロックとunsafe implに安全条件を記す。OS APIと別クレートのテスト用アロケーターの必要なunsafeは、それぞれの所有権・解放・委譲条件をレビューする。
* `significant_drop_tightening`は全ターゲットで有効にし、ロック解放後に実行できる処理を検査する。`redundant_clone`は取得・Spectrumワーカーに加え、STFT・Spectrogram・Lock-in・同期比較のコアとワーカーで有効にし、同じClippyチェックで必須検査する。次は他のコアモジュールやGUIへ段階的に広げる。大きな解析配列のコピー、不要な確保、重い処理を含むロック区間を優先し、所有権と結果の寿命を確認してから必須lintへ昇格する。テストでの意図的な複製や数値照合も一括置換しない。
* 整数サンプル番号は区間の差を取ってから浮動小数点へ変換する。校正後の演算は、中間積のオーバーフロー・アンダーフローと、最終的な振幅・ゲインの有限性まで検証する。無効化後は古いフィルターや平均を引き継がず、正常な完全窓で復帰することを回帰テストで確認する。
* `pedantic`／`nursery`全体は追加監査に使い、一括で必須化しない。数値キャスト・浮動小数点比較・演算の融合・スタック容量は、範囲と精度・再現性・OSごとの制限を検証して個別に採否を決める。`unwrap`の一律禁止も避け、外部入力やI/Oの失敗を握りつぶす箇所を、内部不変条件とテストのassertionから区別して扱う。

完了条件は、再現した不具合の回帰検証と、GUIなし・通常・全機能の共通Rustチェックが通ること。手動GUI・物理デバイス・配布物の受け入れは、これらの静的・数値検証とは別に残す。

* [公開前の最小確認セット](RELEASE_PREPARATION.md#公開前の最小確認セット) を同一候補SHAで判定する。P0は公開前必須、P1は確認または未確認範囲を明記して公開判断とし、未実施の計画項目は未完了のまま残す。USB抜去禁止はこの優先順位とは独立した安全制約である。

完了条件は [配布パッケージの受け入れ](VALIDATION.md#配布パッケージの受け入れ) と公開準備の候補確認を終え、配布範囲と制限を説明できること。タグ・Release・サイト公開は依頼された段階で行う。Rust公開前はダウンロード無効を維持し、Python最終版の`version.json`は変更しない。

### 6：最小の応答測定フロー（未着手）

基本操作と段階4.5／5の受け入れ後に、出力制御と同期比較を使い、2ch REF／応答の最小FRF／Bode用途を作る。初回プロトタイプ配布の必須条件には加えない。

* 測定フローへ入出力の所有権を渡し、手動操作との競合、完了・停止・失敗時の出力停止を定義する。設定復元だけで出力を開始しない。
* 周波数点ごとの励振→整定→取得から始め、既知ゲイン・フィルターを内部→仮想I/O→物理系の順で照合する。
* 条件付き結果、校正・欠落・時計の識別、保存・再実行までを完了条件にする。基本Generatorを再実装せず、THD／IR・連続スイープは個別に計画する。

## 継続する制限

* 公称Fs・未校正FSを基準とする。実時計、物理振幅・CH間位相校正、出力校正、DAC／ADC絶対遅延は未確認または未実装。Scopeの波形軸・トリガーとSpectrogram／XYはFS。
* WindowsはVMware上のGNU／LLD・dev-fast通常版のGUI起動と、iMacのネイティブ起動でMSVC・dev-fast通常版のCLI・GPU読み戻し・GUIウィンドウ生成、qa版の自動UI検証を確認した（[条件](VALIDATION.md#コードで代替できない確認の要約)）。Windows 10のiMacではDx12／AMD RADEON R9 M290Xの読み戻しを確認し、Windows 11とVMの既存確認はMicrosoft Basic Render Driverによるソフトウェア描画に限る。外部I/Oの可変コールバック、接続直後のSingle、全起動・再接続の安定性、物理16ch、Windows／Linux・他機器の測定評価は未確認。設定上限768 kHzは動作保証ではない。
* GPU実行時間・実表示／scanout、反復操作応答、最大Scope区間のコピー・ディスクI/O負荷、qaなし配布物の長時間測定と有限Stop後の監査は評価を残す。UAC-232・48 kHzの600秒release QAは取得・解析・停止監査を通過した一方、撮影なしでも最大約29秒のUIフレーム間隔を観測した。原因は未確定で、取得欠落0と表示応答を区別する。
* Spectrogramは撮影操作が重なった長時間評価でGUI更新の長い停止、STFT転送・Generator内部入力の欠落を観測した。コアにはCPU競合・表示受信停止・再開を含む[負荷耐性QA](VALIDATION.md#コア解析の負荷耐性qa)があり、Lock-inの設定集中、解析の結果公開待ち、STFTの転送・結果収集の余裕を改善した。起動時バックログと端数ブロックを受けるSTFT転送容量を確保し、QA撮影のPNG保存をGUI外へ分離した。CPU競合下の最大設定（768 kHz／16ch）の模擬入力では受付欠落が残り、競合を増やすとLock-in転送にも欠落が出るため、無欠落の受け入れは未達。UAC-232の192 kHz起動時の欠落・GUI停止の原因切り分けと実入出力での耐性評価も残る。模擬入力や限定した負荷試験の成功を物理経路・表示応答の保証へ広げない。
* Live／Latestは最新完全窓の観察で、過渡捕捉を保証しない。512k・48 kHzの完全窓は約10.92秒。表示間引きと入力・解析欠落、窓時間と処理遅延を区別する。
* Spectrogram／XY・カーソル・全CH長時間記録・Spectrum窓の全生入力は結果保存の対象外。PNGはScope／Spectrum。
