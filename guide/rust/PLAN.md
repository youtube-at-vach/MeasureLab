## 現在の到達点

Scope・Spectrum・Spectrogram・XYを同時に使うプロトタイプがある。旧計画の「段階1・2完了」はこの範囲の確認を指し、測定器としての品質、実行責務の分離、全OS・全機器への対応完了を意味しない。現在の実装を維持しながら、ScopeとSpectrumの測定用途を先に完成させる。

| 対象 | 実装されていること | 残る境界 |
| --- | --- | --- |
| 入力 | CPAL、1〜16chの同期フレーム、f64、固定容量SPSCと履歴、内部デモ | デバイス既定のFs。入力キュー消費・履歴更新・デモ生成はUI側 |
| Scope | 最初の2chの表示、全入力CHからのトリガー選択、RMS・Peak・P-P、極値集約、欠落で線を分離 | 表示トレースの任意CH割当と入力校正は未実装。統計は表示区間に依存 |
| Spectrum | 1,024〜32,768点、3窓、入力CH選択、DC除去、指数電力平均、ピーク保持、f64標準／f32選択 | UI側で最新完全窓を最大30回/秒、N/4以上の新規入力ごとに解析。連続窓の網羅・PSD・クロススペクトルは未実装 |
| Spectrogram | 専用STFTワーカー、N/4 hop、独立設定、512行の循環履歴・テクスチャ、欠落表示 | ワーカーへの入力供給はUI側。結果プールにも容量上限がある |
| XY | CH 1×CH 2の同期サンプル、独立した観察幅、Free／Trace Snap | モノラルでは無効、最大32,768点。任意CH割当・残像保持は未実装 |
| 保持・カーソル | 共通Stop、遅着STFT除外、時間・周波数A/B、保持中の表示変更 | 入力世代・窓情報等は各所に分かれ、結果全体の共通モデルは未整備 |
| 配置 | 表示選択、設定アコーディオン、2×2／上下配置 | セッション内のみ。永続化・自由配置・翻訳は未実装 |
| 出力・測定フロー | 内部デモとQA専用の仮想I/O出力 | 通常アプリのGenerator、Software Loopback、Lock-in、応答測定、記録は未実装 |

現状のSpectrumは片側ビン振幅のdBFSで、1 FS peakのビン中心正弦波を0 dBFSとする。窓のcoherent gainを補正し、DCとNyquistは2倍しない。ΔfはFs/N、RBWは窓の等価雑音帯域を表す。PSD・電圧・dBm・独立した可変帯域フィルターとして扱わない。演算のf64と、描画・カーソル読み出しにも使っているf32のdBFS配列を区別する。

停止中の解析設定変更は次回開始用とし、保持中の値の由来を変えない。時間カーソルでSpectrumを再解析する機能はない。欠落・範囲外・未保持の値に別のサンプルを代用しない。再開・入力変更では古いデータと選択を無効化する。

### 既存の検証で分かっている範囲

* GUI非依存の数値テストがあり、FFTの参照比較、f32との差、DCとNyquist、平均、CH 16、トリガー、履歴の折り返し、欠落、カーソルを検証している。
* [2026-10-05の統合記録](validation/PROTOTYPE_2026-10.md#段階2の統合検証2026-10-05)では、macOSでGPU読み戻し、通常幅／狭幅、停止・再開、BlackHole 16ch／2ch切り替え、既知信号と連続動作を確認した。物理入力のユーザー確認も、測定精度全体の保証とは分けて扱う。
* 同記録のBlackHole 96 kHz・16ch・FFT 8,192・4画面・600秒では、取得／STFT入力／結果の欠落は0、UI間隔p95は17.880 ms、eframe処理p95は5.630 ms。最大FFTの別条件では6.120 msであり、CPU 4 ms程度の目安は未達。
* GPU実行時間、取得から表示までの遅延、Windows／Linux実機、物理系の校正精度は未確認。既存記録は当時の実測であり、本計画の更新時に再測定した値ではない。

## 現在の構造と先に解消する課題

```text
CPAL callback → 固定容量SPSC
                     ↓
UI更新: キュー消費 → 共通f64履歴 ← 内部デモ生成
                     ├→ Scopeのトリガー・測定・表示準備
                     ├→ Spectrum FFT・平均・表示準備
                     ├→ XYの区間選択・表示準備
                     └→ 固定容量キュー → STFTワーカー
                                              ↓
UI更新: 結果受信 → Spectrogram履歴 → GPU描画
```

[audio.rs](../../src/audio.rs)はコールバックとデバイス管理を分離している。一方、[app.rs](../../src/app.rs)の`poll_audio`・`poll_demo`・`update_spectrum`はUI更新から呼ばれる。[stft.rs](../../src/stft.rs)の演算が専用ワーカーでも、その入力供給までUIから独立したわけではない。UIが止まると入力の消費が遅れ、有限のキューは飽和し得る。

次の作業はこの実行責務の分離である。Spectrum FFTだけを別スレッドへ移して終わりにしない。UI遅延中にも取得と必要な解析が継続し、表示用の受け渡しが詰まっても測定を待たせないことを確認する。

| 責務 | 所有するもの | 境界 |
| --- | --- | --- |
| Audio I/O | デバイスのサンプル入出力・連番・転送時の欠落 | コールバックは変換と固定容量転送に限定。DSP・UI・保存を待たない |
| 測定コア／DSP | 履歴、CH割当、トリガー、解析、平均、結果の条件・有効性 | UI更新から独立して進める。必要な処理だけ購読し、キュー・メモリの上限を持つ |
| UI／Renderer | 操作要求、表示範囲・色・配置、描画用データ | 一貫した結果を受け取り、表示を間引ける。測定結果の状態をGUI部品に所有させない |
| 非リアルタイム処理 | デバイス列挙・開始終了、設定保存、将来の記録・書き出し | 完了・失敗を通知し、遅いI/Oを測定経路へ持ち込まない |

これは責務の境界であり、一律に測定器ごとにスレッドを作る指定ではない。ワーカー数、履歴の所有、スナップショットの渡し方は3aで最小構成を検証する。既存のSTFTワーカーやFFT計画・scratchの再利用を活かす。

## 次のマイルストーン

旧段階3以降を以下に置き換える。次の実装対象は3a。各項目を個別に検証・レビューできる変更へ分け、前段の測定用途が成立してから次へ進む。段階番号は公開版や期限を示さない。

| 順序 | 完成させる用途 | 次へ進む条件 |
| --- | --- | --- |
| 3a：次 | UI負荷に依存しない取得・解析 | UIを遅延・停止させても取得と必要な解析が継続し、飽和・停止・再開を正しく扱う |
| 3b | 任意の2chをScopeで測る | CH・トリガー・区間・RMS／Peak／P-P・カーソルが既知信号と一致する |
| 3c | Spectrumで振幅と雑音電力を測る | FFT・窓・平均・PSD・帯域積分の定義と許容差を固定し、既知信号で一致する |
| 3d | 同じ条件で基礎測定を再現する | 最小のCH校正・設定保存・結果と条件の書き出しが揃い、復元して同じ結果を得る |
| 4 | Software Loopbackと最小f64 Lock-in | 共通入力経路で振幅・位相・時定数・欠落を検証し、FFTと整合する品質評価を行う |
| 5以降 | 必要な測定フローを一つずつ追加 | 前提となる励振・同期・校正・数値検証を満たす候補から選ぶ |

### 3a：取得・測定コアをUIから独立させる

* 共通履歴、入力の消費、デモ生成、解析のスケジューリングをGUI外へ移す。まず現在のScope／SpectrumとSTFTへの入力経路を保ち、計算グラフの汎用基盤を先行実装しない。
* 結果に入力世代・対象CH・整数サンプル区間・Fs・解析設定・欠落を対応させる。複数表示の読み出し中に条件と値が食い違わない単位で受け渡す。
* 連続解析と、最新窓だけを読む観察モードを区別する。平均・ピーク保持・トリガーが何を対象とした値かを明示し、非表示化だけで測定状態を変えない。
* 表示の更新省略、STFT表示履歴の欠落、測定入力や解析窓の欠落を別々に数える。表示待ちで計算を止めず、処理能力を超えた場合の破棄・無効化・回復を定義する。
* Stop時に保持するサンプルと解析窓、開始・停止・設定変更への応答、終了時のワーカー回収を定義する。遅着結果と同一窓の再平均を防ぎ、既存の保持・カーソル動作を維持する。

完了確認には、通常の1ch・2ch・16chと最大FFT、UIを入力キュー容量相当より長く止める試験、意図的なキュー飽和、非表示、停止・再開、入力切り替えを含める。GUIなしで同じ既知入力を測定し、UI遅延によってコア側の入力連続性・測定値・平均回数が変わらないことを確認する。OSや入力デバイス自体の欠落は別途記録する。

### 3b：CHルーティングとScopeの完成条件

* ScopeのトレースとXYのX/YへCHを割り当てる。既存のトリガー・Spectrum・SpectrogramのCH選択と共通モデルに揃え、表示名と内部IDを分け、同じ時計・フレームの対応を保持する。
* まず同時に扱うScopeトレースは2本とし、1〜16chから選ぶ。CHの入れ替え、存在しないCH、モノラル、デバイス変更によるCH数減少を扱う。
* 測定区間・トリガー位置と補間・生サンプル・描画集約を区別する。RMS・Peak・P-Pやカーソルの値を、見た目の線分から算出しない。
* DC、既知振幅、位相差、短いスパイク、欠落、履歴周回を検証する。表示倍率・幅・配置変更で同じ区間の測定値が変わらず、CH変更時には必要な解析状態を更新する。

### 3c：Spectrumの完成条件

* 現在の振幅dBFSを維持し、窓・FFT長・DC除去・平均方式・更新区間・ピーク保持の意味を表示と数値テストで固定する。指数電力平均の設定値を単純な積算回数と呼ばない。
* PSDを独立した測定モードとして追加する。基準をまずFS²/Hzとし、片側化、窓の電力正規化、DC／Nyquist、帯域積分とRMS²の関係を定義する。振幅スペクトルのラベル変更だけでPSDにしない。
* ビン中心／ビン間の正弦波、2トーン、DC、Nyquist、既知の雑音、短い過渡、欠落、平均リセットを検証する。窓・FFT長を変えても、定義した測定法と許容差内で振幅や積分電力が一致することを確認する。
* 数値結果はf64で保持できる入口を作り、表示用f32のdBFS・ピーク値から精密測定を組み立てない。f32 FFTの誤差と対象信号の制限は別に記録する。
* カーソルにCH・実ビン周波数・単位・寄与区間を対応させる。スナップショット解析で捕捉を保証しない過渡と、連続窓が必要な測定を区別する。

クロススペクトル・相関は2chの解析として次の候補に残す。複素スペクトル、共有する入力区間、位相符号、平均、正規化・遅延の定義を揃えて追加する。これらや高度な歪み解析を、基礎Spectrumの一括実装へ含めない。

### 3d：校正と再現に必要な最小保存

* CHごとのゲイン・オフセット・単位・校正条件を定義し、未校正ではFS／dBFSを使う。校正の識別・版を結果へ固定し、停止後の変更で過去の値の由来を失わない。
* 入力・CH割当・解析設定・校正を安定した内部IDと版付き形式で保存する。測定結果にも単位・区間・設定・欠落を付けて書き出せるようにし、単なる画面設定の保存と区別する。
* 保存→再起動→復元で既知信号を再測定する。デバイス不在、不正値、旧形式、校正変更を検証し、取得・出力・記録を設定復元だけで開始しない。
* 配置・テーマ・翻訳は測定条件と別に扱う。自由配置の完成や全言語への対応を、この段階の前提にしない。dBmは基準と負荷インピーダンスを扱える測定が必要になった段階で追加する。

段階3はScope／Spectrumの定義済み範囲を使える状態にする節目である。外部仮想I/Oでの照合を含め、物理校正など実機が必要な項目は確認範囲と未確認事項を残す。汎用のSoftware LoopbackとLock-inによる経路全体の評価は段階4で行う。

### 4：Software LoopbackとLock-inによる品質評価

* 最小の信号生成→仮想DUT→共通入力→解析を、通常の測定コアで実行する。単なるデモ表示や解析関数への直接入力と区別し、既知ゲイン・位相・遅延・雑音を注入する。
* Lock-inはまず2chの最小用途を決め、基準信号、位相符号、X/Y・振幅の定義、周波数、時定数、フィルター、整定、欠落後の回復をf64で実装する。最初から旧版の関連測定器群を再現しない。
* 微小信号、DC重畳、既知位相、周波数ずれ、雑音、基準喪失を検証する。FFTとの比較は同じ振幅定義・区間・帯域条件で行い、理論値を主な基準にする。
* アルゴリズム単体→アプリ内Software Loopback→BlackHole等→物理デバイスの結果を分けて評価する。機器がない層は未確認とし、測定精度を保証する対象範囲を広げない。

この節目で精度・再現性・UI負荷への独立性・長時間動作を評価し、基礎設計の問題があれば高度測定の追加前に解消する。

## 品質・性能の判定

### 4層の検証と証拠

| 層 | 評価すること | 現在の状態 |
| --- | --- | --- |
| 1：内部演算 | 理論値・独立した参照計算との一致、境界・誤差 | 各Rustモジュールにテストあり。追加測定では定義と許容差を先に決める |
| 2：アプリ内Software Loopback | 信号生成から共通入力・解析までの条件と状態遷移 | 内部デモはある。汎用経路と仮想DUTは段階4で整備 |
| 3：外部仮想I/O | CPAL経路、CH対応、欠落、切り替え、将来の出力 | BlackHole 16ch／2chの既存QAあり |
| 4：物理デバイス | ADC／DAC、機器レンジ、校正、時計差を含む結果 | 物理入力の確認あり。校正精度や新規測定は別途実機検証が必要 |

旧Python版の数値テストは期待値・許容差・測定手法の参考にし、必要なケースをRustで再検証する。旧版との一致だけを正しさの根拠にせず、旧アプリの環境は自動復元しない。画面の確認は数値検証の代わりにしない。

### 性能予算

* 最優先は取得と必要な測定の継続。正常区間で欠落0を確認し、意図的な過負荷では欠落位置・数・結果の無効化が正しいことを確認する。
* 60 Hz表示で16.7 ms/frame程度を目安とする。30 fpsは約33.3 ms/frame。これはUI表示の目標であり、音声コールバックの締切やFFTの解析窓時間ではない。
* フレームのCPU処理は4 ms程度を目安にし、UIとDSPワーカーの時間を別々に測る。ワーカーへ移した時間も総負荷に含め、UIが軽くなっただけで演算が高速化したとはしない。
* UI間隔p95、平均更新頻度、長い間隔の頻度、eframe処理p95、各処理のCPU時間を併記する。個々のp95の差や合計から未計測の処理時間を算出しない。VSync／OSの揺らぎや軸ラベル生成の寄与は、追加計測で確かめる仮説として扱う。
* GPU実行時間と取得から表示までの遅延は独立に測る。窓時間N/Fsや平均の整定時間をFPSと混同しない。
* 固定容量の履歴・キューとプロセス全体のRSSを区別し、初期充填後の推移を測る。停止中は不要な再描画・転送を省く。

比較には、リビジョン、OS・機器、Fs、CH、信号、FFT・窓・精度、表示数・寸法、同期、時間を残す。既存の600秒条件を再利用し、数値検証と負荷計測の条件差を明示する。最適化は正しい参照経路との比較と負荷の実測を揃えて導入する。

## 更新と作業の境界

作業完了時は該当する実装状態・残る境界・次の条件を更新する。結果は成功・失敗・未実施を区別し、実測値を日々この計画へ追記しない。検証コマンドは [Tool Usage Guide](../../.agents/workflows/tool_usage.md)、機能別QAの操作は [README](README.md#検証計測) を使う。

`docs/`と`download-site/`はPython最終版の公開資料、`version.json`は配布版を表す。開発PRのbaseは`rewrite/rust`。取り込み、mainへの切り替え・マージ、タグ作成、公開は依頼された段階だけ進める。
