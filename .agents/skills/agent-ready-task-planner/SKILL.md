# Ready Issue の実装計画

既存 Issue に実装計画の正本を残す。作業ツリーは変更しない。

## 調査する

1. [GitHub 共通手順](../../workflows/github_project.md)で `Ready` の Issue を1件選び、本文・コメント・既存計画を読む。
2. 対象コード、テスト、日英ドキュメントを読む。設計資料は [Agent Guide](../../../AGENTS.md)から対象に関係する節を選び、提案由来なら元の提案も確認する。
3. 変更箇所、既存契約、回帰リスク、確認方法をコード上の事実に結び付ける。

測定系では単位・校正・有限値・品質表示、状態所有者、開始／停止／キャンセル／リセット、callback／worker／GUI の境界を確認する。異常検出や履歴保持は対象に必要なものを選び、既存の共通機能を再利用する。GUI では翻訳と全言語 UI サイズを計画に含める。

## 計画を記録する

通常の実装上の選択は、既存コードと設計指針から決め、前提を明記して進める。閾値、校正、結果の有効性、機器条件などの重要な仕様が決められない場合は、推測せずブロック理由を記録する。作業量の多さや候補選択の迷いだけで Issue を `Blocked` にしない。

書き込み直前に対象がまだ `Ready` であることを確認する。元の本文は残し、次をコメントする。

| 結果 | コメントの内容 | 投稿後の Status |
| --- | --- | --- |
| 計画確定 | `実装計画（正本）`：背景、方針・範囲、ファイル単位の変更、必要な契約・状態遷移、完了条件・検証、参照 | `Working` |
| 仕様未確定 | `ブロック理由`：確認できた事実、判断できない仕様、その影響、再開に必要な回答、参照 | `Blocked` |

計画には関係する UI・翻訳・エクスポートの変更と、正常系・失敗系・回帰の確認方法を含める。[PR 前検証](../ci-prechecker/SKILL.md)を最終検証として参照し、コマンド一覧は複製しない。

以前の計画を置き換える場合は、そのコメントを参照して今回が正本であると明記する。コメントの投稿成功後にだけ Status を変更する。

## 完了

Issue URL、正本またはブロックコメントの URL、Project の最終 Status と未解決事項を報告する。状態更新に失敗した場合は、コメントを再投稿せず状態更新から再開する。
